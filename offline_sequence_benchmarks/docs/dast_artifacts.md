# Подключение к repo-analyzer: постобработка DAST

Модуль `offline_sequence_benchmarks.dast_artifacts` работает после завершения штатного DAST. Он читает только переданные файлы и не требует сети, Docker, доступа к исходникам проверяемого приложения или учётных данных. Q-learning, генетический алгоритм и собственный HTML-стенд остаются исследовательскими модулями, отдельно от продуктовой динамики.

## Точка подключения

Скопируйте папку `offline_sequence_benchmarks/` в корень репозитория анализатора. Когда штатный runner `dynamic` закончит работу, вызовите функцию из слоя постобработки или отчёта. Не заменяйте реализацию `dynamic` и не добавляйте новый runner, документ или пункт UI.

```python
from offline_sequence_benchmarks.dast_artifacts import summarize_artifacts

summary = summarize_artifacts(
    scan_result.meta,
    zap_report=zap_json_path,       # Path готового отчёта этого скана или None
    coverage_trace=trace_json_path, # Path записи тестов этого скана или None
)
```

`zap_json_path` и `trace_json_path` передаёт ваш существующий слой экспорта. Привязывайте пути к текущему `scan_id` на стороне воркера, дождитесь завершения записи и не берите их из полей заявки или URL. Модуль не ищет файлы в `data/`, не меняет `ScanResult` и не публикует артефакты. Если нужна сводка для внутренней диагностики, сохраните её отдельно от `manifest.artifacts`. В продуктовый отчёт можно вывести только агрегаты в существующей секции DAST, если это требуется.

## Входы и интерпретация

- **`ScanResult.meta`**: нужны `runners` и `dast.status`. Если `dynamic` не выбран, функция возвращает `None` и не читает файлы. При `skipped`, `failed` или неизвестном статусе она возвращает статус и не читает файлы. Для завершения принимаются `ok`, `success`, `succeeded`, `completed`, для частичного результата `partial`. Проверьте успешное значение на вашей ветке и при необходимости нормализуйте его только в передаваемой копии метаданных.
- **ZAP JSON**: поддерживается структура `site[].alerts[].riskcode` формата [Traditional JSON Report](https://www.zaproxy.org/docs/desktop/addons/report-generation/report-traditional-json/). Сводка показывает число сайтов и число групп предупреждений по степени риска, а не отдельные срабатывания или уникальные подтверждённые уязвимости. Одна и та же группа на разных сайтах считается отдельно. URL, заголовки, HTML, описания и содержимое запросов не попадают в сводку.
- **Трасса функциональных тестов**: необязательный локальный JSON контракта этого модуля, не штатный формат ZAP. В `episodes` записываются только уже выполненные переходы `[source_state_id, action_id, target_state_id]` как целочисленные идентификаторы. Идентификаторы должны быть стабильны в пределах прогона; соседние переходы внутри эпизода должны стыковаться. Число наблюдавшихся состояний, уникальных переходов и самая длинная трасса описывают только имеющиеся записи. Они не оценивают полноту сканирования и не доказывают уязвимость. На входные трассы лимит лабораторного эпизода `--horizon` не распространяется.
- **Нет данных**: для каждого файла отдельно возвращается `not_provided`, `missing`, `unreadable` или `invalid`, если он не собран или не читается. Это не ноль предупреждений и не нулевое покрытие. Не используйте эту сводку как автоматический вердикт безопасности или как причину откатить SAST/LLM. Максимальный размер одного JSON-файла 16 МиБ.

## Граф наблюдавшихся действий

Построить ориентированный граф можно отдельно, без ZAP и метаданных DAST. Передайте обезличенную трассу уже выполненных функциональных тестов:

```bash
python -m offline_sequence_benchmarks.dast_artifacts \
  --graph-from-trace offline_sequence_benchmarks/examples/coverage_trace.json
```

Входной файл использует тот же контракт `schema_version: 1` и `episodes`. Дополнительные поля не нужны: в частности, не включайте URL, параметры, токены, сетевые запросы или ответы. Решение о том, какие результаты теста соответствуют одному состоянию, принимает экспортирующая сторона: один ID состояния должен обозначать одно и то же состояние во всех эпизодах одного файла.

На выходе JSON с `graph.states`, `graph.start_states` и `graph.edges`. Ребро содержит `source`, `action`, `target` и число его наблюдений `observations`. Повторы объединяются; разные результаты одного действия сохраняются как отдельные рёбра. Между эпизодами рёбра не дорисовываются. Граф показывает только наблюдавшееся поведение: отсутствие ребра не означает невозможность перехода. Режим не запускает и не воспроизводит действия; вывод предназначен для внутренней диагностики, не для передачи сканеру.

## Локальная проверка и CI

Из корня репозитория запустите команду с искусственными примерами из пакета:

```bash
python -m offline_sequence_benchmarks.dast_artifacts \
  --meta offline_sequence_benchmarks/examples/scan_meta.json \
  --zap-report offline_sequence_benchmarks/examples/zap_summary_input.json \
  --coverage-trace offline_sequence_benchmarks/examples/coverage_trace.json
```

Сводка печатается в stdout; `null` означает, что секция `dynamic` не выбрана. `--meta` ожидает непосредственно объект `meta`, а не весь `ScanResult` или произвольный `summary.json`. Для CI можно использовать ту же команду после имеющегося job, подставив пути к финальным артефактам, или ограничиться тестами контракта:

```bash
python -m unittest discover -s offline_sequence_benchmarks/tests -v
```

Спецификация использовалась для выбора слоя подключения. Имена выходных файлов штатного ZAP, успешные статусы конкретной ветки и сериализация объектов воркера на GitHub не проверялись. Для проверки на конкретной ветке нужен обезличенный пример метаданных и экспорта завершённой проверки либо фрагмент кода, который выгружает эти файлы.
