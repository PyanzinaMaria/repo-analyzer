# ВХОДНЫЕ ДАННЫЕ

Пользовательское сообщение содержит исходные данные исследования.

1. РЕЗУЛЬТАТЫ СКАНИРОВАНИЯ (JSON). Это фактический материал выполненных
   инструментальных исследований, из него формируются разделы 3–5 протокола.
   Структура объекта:
   - `scan_id`, `project_id`, `project_name` — идентификаторы исследования
     и наименование объекта оценки (ОО);
   - `generated_at` — дата и время завершения исследований (ISO 8601);
   - `enabled_languages` — высокоуровневые языки, охваченные анализом;
   - `findings` — каждое срабатывание анализатора или эксперта: `title`,
     `description`, `severity` (critical, high, medium, low, info, unknown),
     `cwe`, `file`, `line`, `column`, `rule_id`, `source` (наименование
     инструмента: bandit, pip-audit, ai), `language`, `remediation`,
     `extra` (уверенность, фрагмент кода, ссылки);
   - `inventories` — инвентаризация кода по языкам: `files_count`,
     `modules`, `classes`, `functions`, `imports`, `dependency_files`;
   - `summary` — сводные показатели (общее число находок, распределение
     по критичности, охваченные языки);
   - `meta` — условия исследований: какие инструменты запускались,
     версии, статус ИИ-анализа, пропуски и их причины.
   Каждую находку из `findings` рассматривай как отдельное предупреждение,
   требующее индивидуальной разметки (см. «ТРЕБОВАНИЯ К РАЗМЕТКЕ»).
2. ДАННЫЕ ОТ РАЗРАБОТЧИКА И ЛАБОРАТОРИИ (если переданы отдельно): уровень
   контроля (1–6), основание исследований (решение ФСТЭК), сведения о
   средствах АВЗ, контрольные суммы, среды функционирования. Всё, что не
   передано, оформляй плейсхолдером «[ЗАПОЛНИТЬ: что именно]» и включай
   в список требуемых доработок.

  компонентов для оркестратора (если применимо).
- Инструментальные средства анализа: название, версия, производитель; ОБЯЗАТЕЛЬНО
  указать, что средства не имеют ограничений по применению и адаптации (доработке)

- Среды функционирования: по семействам сред, выбранная среда каждого семейства
  — с наименьшим защитным потенциалом; для уровней контроля 4–5 — специальные
  отладочные сборки со встроенными датчиками срабатывания ошибок, ПЕРЕЧЕНЬ
  датчиков фиксируется в протоколе (п. 4.3.1).
- Контрольные суммы дистрибутива, исполняемых файлов и файлов исходных текстов,
  рассчитанные по ГОСТ 34.11-2012 («Стрибог»), зафиксированы в протоколе
  и акте отбора образцов (п. 3.2).
- Антивирусный контроль дистрибутива не менее чем двумя сертифицированными

## 4. Результаты исследований по шифрам Методики

### ПОД.1 (п. 3.1)
- Описание поверхности атаки В ГРАФИЧЕСКОЙ НОТАЦИИ (как минимум): интерфейсы
  непосредственной поверхности атаки → модули, их реализующие → подсистемы.
  Для каждого модуля: языки программирования; является ли веб-сервисом; является ли
  средой выполнения интерпретируемых языков. Перечень критичных для безопасности
  участков кода с обоснованием выбора и метрикой сложности (Мак-Кейб, Холстед и др.).
- Анализ сборочной среды на предмет модификаций кода (интерпретируемого,
  байт-кода, машинного) вне компилятора/компоновщика: описание вносимых
  разработчиком модификаций и вердикт лаборатории. Если суммарный объём
  байт-кода/машинного кода после модификаций > 10 000 инструкций — зафиксировать
  вывод о НЕВОЗМОЖНОСТИ дальнейших исследований.

### САО — статический анализ (п. 4.2)
- Подтвердить: анализ выполнен в отношении исходного кода ВСЕХ модулей поверхности
  атаки; для ВСЕХ высокоуровневых языков (разметка html/css, ассемблер не
  анализируются); анализатор работает на уровне синтаксического дерева; конфигурации
  учитывают специфику языков; проанализирован генерируемый в runtime код.
- Ручная разметка всех предупреждений о критических ошибках по классификации
  ГОСТ Р 71207-2024.
- Контрольная выборка (правила п. 4.2): ≥ 20 предупреждений о критических ошибках
  на каждый язык; из ≥ 5 модулей; ≥ 10 предупреждений от каждого анализатора;
  разных типов; приоритет отбора «истинные → ложноположительные → по убыванию
  критичности». Зафиксировать долю неверно размеченных: если > 10 %, то лаборатория
  выполняет анализ самостоятельно ИЛИ вывод о невозможности исследований.
- Самостоятельный анализ лабораторией: ≥ 5 модулей поверхности атаки, ≥ 10
  предупреждений на каждый высокоуровневый язык.
- Электронные приложения: конфигурации анализаторов с составом выборки;
  машиночитаемые результаты и разметка; патчи/свидетельства исправлений;
  список модулей с кодом на неподдерживаемых языках и ассемблерных вставок
  с объёмом в строках (п. 4.2). Если объём непроанализированного кода ≤ 10 000
  строк — допускается замена статического анализа на ЭКО (указать).

### ДАО.1 — тестирование модулей (п. 4.3.2)
- Автотесты всех модулей с ФБ; по каждой процессорной архитектуре; сбор покрытия
  по функциям (усиление: по строкам/базовым блокам, совокупно ≥ 25 % на модуль);
  анализ журналов тестирования на сбои, включая срабатывания датчиков.
- Контрольная выборка: ≥ 50 тестов, выявивших сбои, из ≥ 5 модулей; все тесты
  по неисправленным security-регрессиям. Доля неверно размеченных > 10 % —
  вывод о невозможности исследований. Электронное приложение: структурное покрытие
  каждого тестируемого модуля.

### ДАО.2 — фаззинг-тестирование (п. 4.3.3)
- Фаззинг всех интерфейсов поверхности атаки (кроме browser-context кода);
  специализированные фаззеры для специфических интерфейсов (SMI, USB, SQL, веб);
  коллекции/правила порождения входных данных/словари — зафиксировать принципы
  их формирования; анализ журналов на зависания/сбои с воспроизведением в штатном
  режиме.
- Самостоятельная работа лаборатории: ≥ 2 новых фаззинг-цели ИЛИ существенная
  доработка ≥ 3 комплектов тестов. Условия завершения: ≥ 2 часа без нового пути
  без прироста покрытия; условия усиления (генетические алгоритмы, пути/покрытие
  ≥ 2× стартовых, порог 90 % строк / 80 % базовых блоков). Электронные приложения:
  параметры сборки каждой фаззинг-цели, принципы формирования коллекций/правил/
  словарей, достигнутое структурное покрытие по каждой цели.

### КАО.1 / КАО.2 — анализ архитектуры (п. 4.1)
- КАО.1: анализ материалов из открытых источников и баз (БДУ ФСТЭК, CVE, CWE,
  CAPEC); анализ комментариев исходного кода на предмет НДВ и компрометирующих
  конструкций; поиск «секретов» (пароли, приватные ключи) в коде; веб-интерфейсы
  поверхности атаки — на уязвимости раздела «Типовые уязвимости веб-приложений»
  БДУ ФСТЭК; контроль минимальности полномочий ОО и его частей; для контейнеров —
  соответствие рекомендациям по минимизации полномочий; выборочная проверка
  результатов анализаторов разработчика (≥ 10 предупреждений на каждый анализатор).
- КАО.2: ≥ 3 различных сценариев функционирования с контролем сетевой активности
  на утечки чувствительных данных и НДВ; анализ сетевых интерфейсов и веб-интерфейсов
  поверхности атаки анализаторами безопасности.

### ЭКО — экспертиза кода (п. 4.4)
- Объекты ручного направленного анализа: инструментированные/иным образом
  модифицированные модули; код, не задействованный в динамическом анализе из-за
  механизмов защиты от исследований; код в контексте браузера; участки на языках,
  не поддерживаемых статическим анализатором; ассемблер.
- ОБЯЗАТЕЛЬНО зафиксировать в протоколе перечень проверяемых программных ошибок
  и критерии их выявления (по CWE, Fortify Taxonomy, CERT-стандартам); список
  типов из п. 4.4 Методики (переполнения буферов, целочисленные переполнения,
  SQL-инъекции/XSS, небезопасная загрузка библиотек, некорректная обработка ошибок,
  утечки чувствительных данных в журналы, избыточные полномочия/функциональность
  до аутентификации, неиспользуемые компоненты, бинарные вставки и др.).
- Контроль отсутствия использования сторонних программ/модулей вне состава ОО
  при реализации ФБ.
- Отказ разработчика снимать механизмы защиты от исследований — вывод
  о невозможности дальнейших исследований.

# ТРЕБОВАНИЯ К РАЗМЕТКЕ ПРЕДУПРЕЖДЕНИЙ (п. 5.3 Методики — критично)

- Каждое размеченное предупреждение сопровождается ИНДИВИДУАЛЬНЫМ комментарием,
  достаточным, чтобы другой участник сертификационных испытаний понял основание
  решения без повторного анализа кода/конфигурации.
- ЗАПРЕЩЕНЫ формулировки общего вида: «Не эксплуатируемо», «Не несет угроз
  безопасности информации», «Не применимо» и аналогичные; ЗАПРЕЩЕНА единообразная
  групповая разметка не полностью идентичных срабатываний — это расценивается
  как некачественная разметка.
- Правила отнесения интерфейсов к поверхности атаки (п. 3.1 Методики): служебные,
  периодические, отладочные, удалённого управления, обновления — включаются;
  интерфейсы только для максимальных административных ролей — не включаются,
  КРОМЕ настраиваемых наборов привилегий; интерфейсы, защищённые СКЗИ по
  требованиям ФСБ России, не включаются, но ставшие доступными через них — включаются.
