# Роль LLM в pentest-агенте

Короткий ответ: **LLM — это «мозг», а не «руки»**. Он не отправляет запросы в
приложение и не «нажимает» на уязвимости сам. HTTP-пробы выполняет наш
детерминированный Python-код; LLM решает, **что проверять**, **какой следующий
шаг сделать** и **подтверждать ли сработавшую находку**.

## Три роли LLM

| Роль | Что делает | Кто выполняет действие |
|---|---|---|
| **1. Ревью кода → гипотезы** | Читает код (обзор репозитория + окна кандидатов или сам вызывает `read_file`/`grep`) и говорит: «здесь, вероятно, SQLi, файл `db.py`, строка 40, endpoint `/login`, параметр `username`» | никто — это статическая гипотеза |
| **2. Планировщик (опционально)** | В режиме `tools` выбирает следующий шаг из **фиксированного набора инструментов**: `crawl`, `probe_headers`, `probe_endpoint`, `send_request`, `finish` | инструменты выполняет наш код |
| **3. Судья (judge)** | Когда детектор сработал, смотрит гипотезу + payload + ответ и выносит `confirmed` / `refuted` / `uncertain` — фильтр ложных срабатываний | запрос уже отправлен кодом |

### 1. Гипотезы

LLM получает контекст, построенный без него: индекс tree-sitter, граф вызовов,
точки входа, каталог опасных вызовов `sinks.yaml` и фрагменты кода вокруг
кандидатов. Его задача — отобрать реальные подозрительные места и привязать их
к маршруту и параметру. Результат — `VulnHypothesis` с полями `vuln_class`,
`file`, `line`, `endpoint`, `param`, `confidence`.

### 2. Планировщик

В агентном режиме (`review_tool_mode: on`) LLM вызывает инструменты через
function calling. Инструменты детерминированные: `crawl` обходит ссылки/формы,
`probe_endpoint` запускает плагины, `send_request` делает один запрос. LLM не
может выполнить произвольный код или обратиться в сеть — только выбрать
разрешённый инструмент и его аргументы.

### 3. Судья

Детекторы работают по сигнатурам (ошибка БД, `root:x:0:0`, маркер команды,
`Location: evil.example`, отражение payload в HTML). Если сигнатура сработала,
LLM-судья смотрит контекст и может **опровергнуть** ложное срабатывание.
Важное ограничение: судья **не может подтвердить** то, чего не увидел детектор,
и не может выдумать находку.

## Что LLM НЕ делает

- не отправляет HTTP-запросы и не имеет доступа к сети;
- не выбирает payload'ы «из головы» — их задают плагины;
- не подтверждает уязвимость без сработавшего детектора;
- не пишет в отчёт без evidence (request/response);
- не нужен для работы конвейера: без ключа всё работает детерминированно.

## «Надавливает» не LLM, а верификатор

Цепочка для каждой гипотезы:

```
гипотеза → плагин (SQLi/XSS/traversal/…) × стратегия (raw/urlencode/…)
        → HTTP-запрос на endpoint+параметр
        → детектор проверяет ответ
        → LLM-judge подтверждает или опровергает
        → Finding(source=pentest) с evidence
```

Примеры payload'ов, которые отправляет именно код: `'` и `' OR '1'='1` (SQLi),
`<script>alert(...)</script>` (XSS), `../../../../etc/passwd` (traversal),
`; echo PENTEST_CMD_...` (command injection), XML с внешней сущностью (XXE),
`https://evil.example` (open redirect).

## MCP: где он и зачем

MCP **не используется** внутри работы LLM. Внутри — обычный function calling
провайдера (Groq / GigaChat / OpenRouter / Gemini / Ollama).

MCP-сервер (`app/dast/agent/mcp_server.py`) — это **внешний интерфейс**: те же
инструменты (`crawl`, `probe_endpoint`, `send_request`, `finish`) можно
подключить к Claude Code, Cursor или другому MCP-хосту, чтобы они управляли
нашим агентом. Внутренний конвейер от MCP не зависит.

## Режимы работы

| Режим | Что происходит | Когда использовать |
|---|---|---|
| `direct` (`review_tool_mode: off`) | один запрос: обзор репозитория + окна кода кандидатов → JSON с гипотезами | бесплатный Groq (8k TPM), медленные провайдеры |
| `tools` (`review_tool_mode: on`) | агентный цикл с `read_file`/`grep`/`submit` через function calling | GigaChat, платные ключи, локальная Ollama |
| без ключа | детерминированное ревью: те же плагины, эвристики и отчёты | всегда, как fallback |

Провайдеры и ключи: [LLM_PROVIDERS.md](LLM_PROVIDERS.md).

## Границы: это не полный пентест «как человек»

Чего пока нет:

- многошаговых цепочек эксплуатации (доступ → повышение привилегий → закрепление);
- reverse shell и пост-эксплуатации;
- полноценной проверки бизнес-логики и IDOR/авторизации;
- браузерного движка для SPA/JS-приложений;
- обхода WAF и продвинутых фильтров (есть базовые стратегии кодирования);
- сложной аутентификации (MFA/SSO; логин/регистрация поддерживаются).

То есть по классификации это **активный DAST + verification-агент** с
LLM-ревью кода и LLM-judge: он автоматически проверяет гипотезы и даёт
доказательства, но не заменяет человека в комплексном пентесте.
